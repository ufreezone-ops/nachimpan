## 1. 조사 범위와 집계

현재 `dev`의 `nachimpan_app.py` 17,155행을 정적으로 조사했다.

| 컨트롤 | 코드 호출 지점 | 관리 방법 |
|---|---:|---|
| `st.button` | 56 | 아래 기능별 8분류 관리 |
| `st.form_submit_button` | 2 | 입력·실행 컨트롤로 별도 표기 |
| `st.download_button` | 4 | 데이터 처리·내보내기 컨트롤로 별도 표기 |
| `st.popover` | 33 | 일반 버튼과 별도 컨트롤로 관리 |

**조사 범위의 보완:** 2026-11-28 인수인계 기록의 더 넓은 상호작용 컨트롤 조사에는 raw HTML `<button>` 2개, `st.radio()` 1개, `st.pills()` 5개, `st.checkbox()` 6개도 확인되어 있다. 이 14개 호출 지점은 위 표와 8개 기능 분류의 상세 목록에 아직 편입되지 않았다. 따라서 이 문서는 `st.button` 56개와 form/download/popover의 1차 관리대장이며, 앱 전체 상호작용 컨트롤의 완전한 목록으로 간주하지 않는다. 후속 보완 때 각 컨트롤의 역할과 관리 범위를 확인한다.

위 수치는 소스의 호출 지점 수이며, 반복문으로 생성되는 실제 화면 버튼 개수와 같지 않다. `st.popover`는 버튼처럼 보이는 트리거가 있더라도 일반 `st.button`과 동일한 컨트롤로 합산하지 않는다.

## 2. 기능별 8분류

분류는 외형이 아니라 **사용자가 버튼을 눌렀을 때 수행되는 주된 기능**을 기준으로 한다. 한 버튼이 여러 효과를 내더라도 관리대장에는 주 기능 하나를 대표 분류로 지정하고, 부수 효과는 비고에 기록한다.

| 분류 | 기능 | 포함 기준 |
|---|---|---|
| B1 화면 이동 | 탭·화면·원래 위치 이동 | 주 화면 전환, 다음 화면, 복귀 |
| B2 모드 전환 | 기본·고급모드 변경 | `advanced_mode` 상태 변경 |
| B3 나침반 연결 | 나침반을 통해 자료·출처·설명 창 진입 | 제목+🧭, 출처 안내, 통계 비교 설명 |
| B4 자료 탐색 | 자료 목록 안에서 자료 선택·이동 | 이전/다음 자료, 검색 결과, 읽은 자료, 추천 자료 |

## 4. 기본·고급모드 전환 버튼 3종 비교

### 4.1 사이드바 — 양방향 토글

- key: `sidebar_mode_toggle_btn`
- 라벨: 현재 고급모드이면 `🌿 기본 모드로 전환`, 기본모드이면 `🧭 고급 모드로 전환`
- 동작: 현재 `advanced_mode` 값을 반전한 뒤 rerun
- 특징: 현재 위치·화면을 별도로 첫 탭으로 이동시키는 코드는 이 버튼 처리 안에 없다. 실제 화면 유지 여부는 Streamlit rerun 및 페이지 렌더링 흐름과 함께 검증한다.

### 4.2 기본모드 AI 시선 — 고급모드 진입 초대장

- key: `btn_unlock_advanced`
- 위치: `AI 시선` 기본모드의 고급모드 초대장 아래
- 동작: `advanced_mode=True`; 이전 출처·연결창 복귀용 잔여 상태를 정리하고, 첫 탭·화면 상단으로 이동한 뒤 rerun
- 설계 의미: 단순 토글이 아니라 기본모드에서 고급모드로 들어가는 안내·초대 동선이다.

### 4.3 고급모드 하단 — 기본모드 복귀

- key: `btn_lock_basic_bottom`
- 위치: 고급모드 화면 하단
- 동작: `advanced_mode=False`; 첫 탭·화면 상단으로 이동한 뒤 rerun
- 설계 의미: 고급모드 탐색을 마치고 기본 경험의 시작점으로 돌아가는 명시적 복귀 동선이다.

### 4.4 추가로 발견한 모드 상태 변경

대표사례 `32세 여성` 및 `45세 여성` 버튼은 `apply_case_payload`를 호출한다. 해당 함수 내부에서 `advanced_mode=True`로 설정한다. 이는 별도의 모드 전환 버튼은 아니지만, 사례 불러오기가 모드 상태까지 바꾸는 부수 효과이므로 전체 모드 흐름 검증에 포함해야 한다.

## 5. 외형·색상·연결 관계·위치의 4대 관리 기준

각 버튼은 기능 분류와 별개로 아래 네 축을 모두 관리한다.

1. **외형:** 테두리, 모서리, 배경, 글자, 크기, 패딩, hover
2. **색상:** 기본·활성·비활성·hover, 라이트·다크 모드 대비
3. **연결 관계:** 이동, 상태 변경, 자료 열기, 복귀, 이전 위치 보존
4. **위치:** 정렬, 간격, 부모 컨테이너, PC·모바일 배치

기능이 같은 버튼이라고 외형을 무조건 같게 만들지 않는다. 2호선형 액션 버튼, 제목형 나침반 연결, 자료 탐색 카드, 텍스트 링크형 컨트롤은 서로 다른 UI 패턴으로 유지할 수 있다.

## 6. 1차 조사에서 발견한 후속 과제

### 6.1 부동산 버튼 폭 규칙

현재 CSS에는 `housing-price-dialog-actions` 안의 연결·닫기 버튼에 PC 120px, 480px 이하 104px 고정 폭을 주는 규칙이 있다. 반면 2호선형 공통 규격의 다른 세 버튼은 문구와 패딩에 따른 자동 폭(`max-content`)을 사용한다.

- 현재 코드 사실: 부동산 하단 버튼은 고정 폭 규칙을 적용 중이다.
- 현재 규격 문서 사실: [버튼_외형_표준규격.md](버튼_외형_표준규격.md) 3절도 PC 120px / 모바일 104px로 기록한다.
- 정리 필요: 과거의 '버튼 폭은 글자 수+여백으로 결정, 고정 폭 금지'라는 공통 원칙을 부동산 하단 버튼에도 적용할 것인지, 해당 창의 예외를 유지할 것인지 설계 의도를 확인한다. 코드가 현재 그렇게 되어 있다는 이유만으로 설계 결정을 대신하지 않는다.

### 6.2 공통 CSS 중복 선언

- `nachimpan_app.py`의 약 13,880행 부근에 부동산 하단 버튼까지 포함한 2호선형 공통 버튼 CSS 블록이 있다.
- 약 15,900행 부근에는 자료보기 연결·연결창 닫기·통계 복귀 세 버튼에 대한 공통 외형·자동 폭 CSS가 다시 선언되어 있다.
- 후행 블록은 앞선 블록의 세 버튼 규칙과 상당 부분 겹치지만, 부동산 버튼 규칙까지 포함하는 동일 블록은 아니다.
- 선언 순서와 실제 적용 대상을 대조한 뒤 통합 여부를 판단한다. 이 초안 조사에서는 CSS를 변경하지 않았다.

### 6.3 key와 중복 관리

- 일부 버튼은 명시적 key가 없다.
- `close_housing_price_method_dialog`처럼 동일 key가 두 조건 분기에서 반복 선언되는 사례가 있다.
- 동적 반복 버튼은 key 패턴과 반복 인덱스의 안정성을 별도로 검증한다.
- 후속 대장에는 각 컨트롤의 코드 블록 ID, 부모 컨테이너 key, 실제 CSS 선택자, 콜백/상태 변경, PC·모바일 확인 여부를 추가한다.

### 6.4 화면 검증 원칙

소스의 CSS 선언은 실제 렌더링 성공을 증명하지 않는다. 선언값·Computed 값·실측 박스 크기를 구분하고, PC 및 iPhone 화면에서 외형과 동작을 각각 확인한다. 검색 버튼의 현재 색상·외형은 사용자가 만족한다고 확인했으므로, 별도 근거 없이 임의 변경하지 않는다.
